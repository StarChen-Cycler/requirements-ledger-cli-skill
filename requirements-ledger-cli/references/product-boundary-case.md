# 案例：需求台账的产品定位与任务边界

本案例整理自产品拥有者在 2026-10-31 对通用性评估的澄清，用于解释 reqledger 的设计意图与使用边界。它是产品定位说明，不是命令手册、新增功能规格或所有项目必须照搬的工作流程。命令协议仍以当前 CLI 的 `--help` 为准。

## 1. 要解决的问题与目标用户

目标使用方式是：**一个产品拥有者带领多个 AI Agent 开发项目，在持续迭代中有效承载、记录并管理需求。** 不以多人跨机器实时协作为目标。

台账需要回答：当前要做什么、为什么做、依据哪里、包含和排除什么、怎样判断达标、当前确认和交付记录是什么，以及后来改了什么。需求记录应明确、可读、可追溯；生命周期事实由 CLI 维护。

前期澄清需求能够为架构取舍提供依据，减少因遗漏和误解导致的大规模返工；它不能保证架构永不调整，也不能消除未来业务变化。稳定上线后，预期以局部功能、细节完善和 Bug 修复为主，需求规模逐步增长，而非持续爆炸式扩张。

## 2. CLI、人与 Agent 各自负责什么

| 事项 | CLI 的职责 | 人、Agent 或外部系统的职责 |
| --- | --- | --- |
| 需求内容 | 接收完整输入，执行字段、引用及生命周期门禁，保存可读内容和历史 | 产品拥有者或获授权的 Agent 澄清意图、来源、必要性、范围、边界与可核对的验收条件；判断业务语义是否成立 |
| 编号、版本和状态 | 自动管理编号、修订、状态变化、基线、变更及事务一致性 | 调用方选择正确台账，依据真实事实和授权提交操作，核对回显 |
| 实际开发、构建、测试、部署 | 记录需求和相关进展、结果声明、证据定位 | 开发 Agent、工具链或有权执行的人完成实际工作；工具不代执行，也不判断实际工作已完成 |
| 模型和算法评测 | 记录评测要求、被声明的结果及相关版本或证据定位 | 外部 benchmark 与评测流程完成真实评测、随机性控制、数据集和模型版本验证；不要求把这些能力集成进 CLI |
| 审核、验收、发布 | 固定对应对象、版本和当次声明，保留历史 | 被项目授权的审核者或验证流程实际核对，调用方如实登记；不因更换 Agent 标识就形成独立验证 |
| 正式签署、权限和认证 | 保存归因信息与可供引用的过程记录 | 产品拥有者、可信验证方或认证方定义身份、授权、签署及证据采信规则 |
| 需求变化 | 保存修订、差异和变更闭环，不覆写旧历史 | 有权决定的人或 Agent 判断改变的必要性、影响和取舍，完成所需实现与复验 |

这里的“外部职责”不等于每一步都必须人工执行；可以由获授权的 Agent 或可信工具承担。产品决策权、执行权限与复核安排由项目和会话授权决定，skill 不额外制造逐项人工批准流程。

CLI 对自身保存、引用和事务一致性的检查属于记录工具职责；对项目交付物的实际测试、真实性验证和证据核验属于外部职责。两者不能混为一谈。

## 3. 跨应用通用性与多个台账

需求管理模型不绑定特定行业或应用技术栈，可承载网站、后台服务、桌面软件、APP、游戏、AI 应用及基础设施需求。没有页面的需求按实际全局或非页面归属表达，不为通过门禁而虚构页面。

**单 MD 的含义是每个台账一份权威 MD，不是整个工具、整个目录或所有产品只能有一个台账。** 多产品或需要独立维护的交付版本，可以各自建立台账，由同一个 CLI 分别操作；不要把互不相同的产品承诺强塞进一个台账。

同一产品的顺序迭代可继续沿用同一台账的修订、基线和历史；需要并行独立维护的产品线或版本，可划分成独立台账。台账划分依据独立范围和生命周期，不必按每次小修订新建台账。

每份台账当前只有一个有效基线。多份台账之间的共享约束、版本对应关系与一致性由人或 Agent 组织，CLI 不自动建立跨台账事务或依赖闭包。多团队可按独立边界分别使用台账，这不意味着提供多人跨机器协同写入服务。

## 4. 一个拥有者与多个 Agent 如何长期使用

多个 Agent 可以分工理解需求、开发、评测和复核；同一份权威台账的提交按串行方式协调。已有锁和修订冲突检查用于维护文件一致性，不是跨机器协作或权限系统。

正常工作场景是阶段性提交明确需求，随后记录变更、实现和验收事实；不要求把每个工具调用、临时操作或 Agent 工作指令都变成产品需求。Bug 若暴露原需求未满足，应关联原需求和对应修复、复验事实；若要改变原承诺，再明确修订或变更，不以修复之名偷偷扩大范围。

上一轮存储与执行效率优化已面向这种使用方式完成。本案例不把全账读写直接判为产品不适用，也不提出实时协作、数据库或无限扩容要求。技术上单文件仍保留历史、完整读取与替换，不能据此承诺任意规模恒定耗时或内存；出现真实的阶段性使用瓶颈时，再以实际台账和验收指标评估。

CLI 运行在开发环境，应用的目标运行平台与台账工具的运行平台分开判断。具体 Python、文件系统和平台支持以当前版本说明为准，不在此重复或扩大验证范围。

## 5. 探索性需求可以明确，结果可以未知

探索不是不能入账。需要明确的是要验证什么、允许做什么、怎样判断结果、产出什么和何时结束；不必预先保证被验证方案一定成功。

例如，“多开 worktree”只写出了一个动作。可以在原始来源和范围明确后，将一项基础设施或验证需求表述为：为隔离比较两个候选实现，在独立 worktree 中执行约定验证，交付可复现的观察、比较结果和可行或不可行的结论；明确隔离范围、验证对象、结束条件及清理或保留安排。具体方案、指标与权限由该项目确定，不把本例的数量或做法设为其他项目的固定要求。

验收应判断约定的验证是否完成、证据和结论是否齐全，而不是只接受“方案成功”这一种研究结论。若 worktree 只是实现既有需求的临时手段，可作为任务处理，不自动另建产品需求。

## 6. 三条不能混淆的结论

1. **通过字段检查不等于需求正确。** 结构完整仍可能有业务错误、缺失场景或无法满足的验收条件，需由人或 Agent 实际审阅。
2. **记录“验收通过”或“已发布”不等于真实测试通过或产品已经上线。** 台账保存的是声明与定位，实际工作及验证由外部完成。
3. **记录证据不等于执行或核验证据。** CLI 可以要求填写并保存证据说明或位置，不负责访问、执行或证明其真实性，也不要求将全部评测原始产物嵌入台账。

台账可以在外部规则下作为证据材料，用于支持身份、授权或交付过程的核验；其操作者字段和完整历史本身不完成身份认证，也不自动产生可信签署或认证效力。

## 7. 如何使用本案例

在讨论通用性、规划能力扩展、划分台账或审查责任归属时读取本案例。把外部开发、benchmark、认证和协作需求误列为 CLI 缺陷前，先核对它是否属于本工具的既定职责。

判断工具是否达标，应看它能否明确承载需求、可靠保存需求、维护可追溯的需求生命周期，并在目标串行使用场景下及时响应、遇到问题明确报错。新的能力扩展需来自明确需求，不因能想象到某种场景就自动加入产品范围。
